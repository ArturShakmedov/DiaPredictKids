# NDST

Платформа ранней оценки факторов риска сахарного диабета у детей.

Логотип — только название проекта, без графического знака.

Фронтенд: HTML + CSS + vanilla JS, без сборки и без npm-зависимостей.
Бэкенд: FastAPI и SQLite. Расчёт оценки идёт в браузере; на сервер анкета
попадает только по явному нажатию «Сохранить».

Два кабинета: врача (`/doctor`) и пациента (`/patient`). Кабинет пациента ведёт
родитель — он заводит профили детей и видит их историю. Имя ребёнка живёт только
там: врачу оценка по-прежнему приходит без имени, под случайным кодом.

## Запуск

```bash
pip install -r requirements.txt
python run.py          # http://localhost:8080
```

Автоперезагрузка выключена: на этой машине uvicorn замечал правку и печатал
«Reloading…», но дочерний процесс не поднимался — сервер молча продолжал
отдавать старый код. После изменений в `backend/` перезапустите сервер вручную;
включить автоперезагрузку обратно можно через `NDST_RELOAD=1`.

При первом запуске создаётся `data/ndst.db` и две демонстрационные учётки:

| Кабинет | Почта | Пароль |
|---|---|---|
| врача | `demo@ndst.app` | `demo12345` |
| пациента | `parent@ndst.app` | `parent12345` |

Чтобы наполнить оба кабинета данными для показа:

```bash
python -m backend.seed 80
```

Команда добавляет оценки для кабинета врача и заводит демо-родителю двух детей
с историей анкет — иначе кабинет пациента открывается пустым. Повторный запуск
детей не дублирует.

База, созданная более ранней версией, обновляется на месте: недостающие колонки
`assessments.parent_id` и `child_id` досоздаются при старте, данные сохраняются.

Ключ подписи сессий создаётся в `data/session_secret.txt` при первом запуске;
`NDST_SECRET` задаёт его явно. Перед публикацией стоит задать
`NDST_SEED_DEMO=0`, чтобы демо-учётки не создавались.

## Railway

Сборка идёт по `Dockerfile`, настройки деплоя — в `railway.json`: проверка
здоровья по `/healthz`, перезапуск при падении, ровно одна копия сервиса
(счётчик попыток входа живёт в памяти, а SQLite — на одном диске).

Порядок:

1. Создать сервис из репозитория или командой `railway up` из корня проекта.
2. **Подключить Volume с путём монтирования `/data`.** Там лежат база, код
   клиники и ключ подписи сессий. Без Volume всё это стирается при каждом деплое.
3. Settings → Networking → Generate Domain.
4. По желанию задать `NDST_SEED_DEMO=0` — тогда демо-учётки не создаются,
   а код клиники для первого врача печатается в логах деплоя. Первый
   зарегистрированный врач становится администратором.

Если задана переменная `PORT` (Railway задаёт её сам), сервер слушает
`0.0.0.0:$PORT`, доверяет `X-Forwarded-For` от прокси и помечает cookie `Secure`.
Ключ подписи сессий без `NDST_SECRET` создаётся в `/data/session_secret.txt`
и переживает деплой.

PDF на сервере готовит браузер, и в контейнере Railway его нет — кнопка
«Скачать PDF» предложит сохранить сводку через печать. Если браузер всё же
установить, одновременно работает один (`NDST_PDF_SLOTS`), а один IP может
запросить не больше пяти файлов за пять минут.

## Показать сайт заказчику

```bash
python share.py start    # запустить в фоне с присмотром, напечатать ссылку
python share.py status   # что работает, сколько было перезапусков
python share.py stop     # остановить всё и снять задание планировщика
```

`start` поднимает сервер, открывает наружу https-адрес вида
`https://<имя>.ngrok-free.dev` и печатает ссылку вместе с демо-доступами —
этот блок можно переслать целиком. Терминал после этого можно закрыть.

### Как устроен присмотр

Сервер и ngrok запускает отдельный процесс-присмотр. Раз в 5 секунд он
проверяет `/healthz`, раз в 5 секунд — локальный API ngrok и раз в минуту —
сам публичный адрес. Упавший процесс перезапускается сразу, зависший — после
трёх неудачных проверок подряд. Если процесс падает сразу после старта
(нет интернета, занят порт), пауза перед следующей попыткой растёт до минуты,
чтобы не молотить перезапусками.

Сам присмотр запускает Планировщик заданий Windows (задание `NDST share`),
а не терминал. Так он не умирает вместе с окном или сессией, из которой его
запустили. За самим присмотром следит повтор задания раз в минуту: пока
присмотр жив, повтор игнорируется, а если его убить — через минуту поднимется
новый и заберёт себе сервер и туннель.

Проверено вручную: убитый сервер поднимается через 4 секунды, убитый ngrok —
через 5 с тем же адресом, убитый присмотр — меньше чем через минуту.

**Задание повторяется бесконечно, поэтому после перезагрузки и входа
в систему сайт поднимется сам** и снова станет доступен по ссылке. Это
следует из устройства триггера, но перезагрузкой не проверялось. Чтобы сайт
не открывался наружу, нужен `python share.py stop` — он снимает задание.

Журналы лежат в `data/`: `share.log` — что делал присмотр, `server.log`
и `ngrok.log` — вывод процессов. Каждый обрезается после 5 МБ.

Без `start` присмотр можно запустить и прямо в терминале: `python share.py` —
тогда он живёт, пока открыто окно, и останавливается по Ctrl+C.

Чем `share.py` отличается от `run.py`:

- `NDST_SECRET` берётся из `data/share_secret.txt` (создаётся при первом
  запуске) и переживает перезапуск — иначе заказчик посреди показа оказался бы
  на странице входа;
- `NDST_COOKIE_SECURE=1`: наружу сайт отдаётся по https, cookie помечаются
  `Secure`. На `localhost` это ничего не ломает — браузеры считают его
  доверенным источником.

Что стоит знать:

- **Адрес постоянный.** На этой учётной записи ngrok выдаёт постоянный домен
  (`*.ngrok-free.dev`) — при перезапусках ссылка та же, её можно отправить
  заранее. Если ngrok когда-нибудь выдаст другое имя, присмотр запишет его
  в `share.log`, а `python share.py status` покажет текущее.
- **Один агент ngrok на учётную запись.** Бесплатный тариф не даёт поднять
  второй туннель, поэтому при старте присмотр гасит оставшиеся процессы ngrok
  и освобождает порт сервера от хвостов прошлых запусков. Если ngrok нужен
  параллельно для чего-то ещё, этот присмотр ему помешает.
- **Заглушка ngrok.** На бесплатном тарифе при первом заходе показывается
  страница-предупреждение: нужно один раз нажать «Visit Site».
- **`--host-header` менять нельзя.** Сервер сверяет `Origin` с `Host`
  (`deps.check_origin`), и подмена `Host` на `localhost` сломала бы вход и
  сохранение анкеты с ошибкой 403. По умолчанию ngrok передаёт свой домен
  в обоих заголовках, поэтому проверка проходит.
- **Ссылка доступна всем, у кого она есть.** Данные в базе демонстрационные,
  но демо-пароли лежат в этом файле — если за ссылкой окажутся реальные
  анкеты, пароли нужно сменить, а `NDST_SEED_DEMO=0` отключит демо-учётки.

Требуется ngrok с привязанным токеном:

```bash
winget install Ngrok.Ngrok
ngrok config add-authtoken <токен из личного кабинета ngrok>
```

## Адреса

| Адрес | Страница | Доступ |
|---|---|---|
| `/` | лендинг | всем |
| `/assessment` | анкета и результат | всем |
| `/login` | вход врача | всем |
| `/register` | регистрация врача по коду клиники | всем |
| `/patient/login` | вход родителя | всем |
| `/patient/register` | регистрация родителя | всем |
| `/doctor` | кабинет: сводка | по сессии, иначе `302 → /login?next=<адрес>` |
| `/doctor/assessments` | список оценок с фильтрами | по сессии |
| `/doctor/risk` | анализ риска | по сессии |
| `/doctor/stats` | статистика | по сессии |
| `/doctor/knowledge` | база знаний | по сессии |
| `/doctor/settings` | настройки | по сессии |
| `/patient` | кабинет пациента: сводка | по сессии, иначе `302 → /patient/login?next=<адрес>` |
| `/patient/history` | история оценок и привязка по коду | по сессии |
| `/patient/children` | профили детей | по сессии |
| `/patient/recommendations` | рекомендации по последней анкете | по сессии |
| `/api/docs` | документация API | всем |

У каждого раздела кабинета свой адрес: ссылку можно скопировать, открыть
в новой вкладке и вернуться кнопкой «назад». Переход между разделами идёт
через `history.pushState`, страница при этом не перезагружается. Неизвестный
раздел отдаёт `404`, `/doctor/overview` — `301` на короткий `/doctor`,
а старые ссылки вида `/doctor#patients` клиент переписывает на новый адрес.
Отдельного раздела «Пациенты» нет: система хранит оценки без имени ребёнка,
поэтому это одна сущность и один список. `/doctor/patients` отвечает `301`
на `/doctor/assessments`.
Кабинет пациента устроен так же: `/patient/overview` — `301` на `/patient`,
неизвестный раздел — `404`.

Если сессии нет, адрес раздела сохраняется в `next` и после входа человек
попадает именно туда, откуда пришёл.

У врача и родителя **разные cookie** (`ndst_session` и `ndst_parent`) и разные
поля в подписанной нагрузке, поэтому токен одной роли не подойдёт другой,
а войти в оба кабинета одновременно можно — это удобно при показе.

Старые адреса с `.html` отвечают `301` на канонические, адрес с завершающим
слэшем — тоже. Несуществующий путь отдаёт страницу `404.html`, а под `/api/` — JSON.

`cabinet.css` — общий каркас обоих кабинетов: сетка, боковая панель с
выдвижением на телефоне, верхняя полоса, плитки, панели и таблицы. `patient.css`
добавляет то, чего нет у врача: выбор ребёнка, шкалу последней оценки, карточки
детей и блок рекомендаций. `auth.js` обслуживает все три формы входа и
регистрации — адрес запроса и адрес возврата заданы атрибутами `data-auth-url`
и `data-auth-home` на `<body>`.

Адреса статики совпадают с именами папок, поэтому по ссылке видно, где лежит
файл: `frontend/styles/base.css` отдаётся по `/styles/base.css`,
`frontend/scripts/i18n.js` — по `/scripts/i18n.js`. Страницы из `frontend/pages`
доступны по чистым адресам без расширения (таблица выше).

Единственная внешняя зависимость — шрифт Inter с Google Fonts. Без интернета
сайт работает на системном fallback-шрифте.

## Языки

Русский, узбекский (латиница) и английский. Переключатель — в шапке и в мобильном
меню; выбор запоминается в `localStorage` под ключом `ndst.lang`, при первом
заходе язык берётся из настроек браузера.

Ключом в словаре служит сам русский текст, размечать HTML не нужно: движок
обходит текстовые узлы и переводимые атрибуты (`placeholder`, `aria-label`,
`title`, `alt`), а также `<title>` и meta description. Русский остаётся в разметке
как исходник и как запасной вариант, если перевода нет.

Как добавить строку: написать её по-русски в HTML и добавить пару
`'русский текст': 'перевод'` в `D.uz` и `D.en` внутри `frontend/scripts/i18n.js`.

**Браузерный переводчик отключён намеренно.** На страницах стоит
`<meta name="google" content="notranslate">`. Причина не в упрямстве: Google
Переводчик подменяет текстовые узлы своими, движок теряет ссылки на исходники,
и после автоперевода кнопки RU / UZ / EN перестают работать. Сайт и так
выходит на трёх языках, поэтому выбор сделан в пользу своего переключателя.

Название проекта дополнительно помечено `translate="no"` — и в логотипе, и в
заголовке главной. Имя не переводят и не транслитерируют. Этот атрибут
уважает и наш движок: текст внутри такого элемента он не трогает.

Динамические экраны (результат анкеты, таблица кабинета) собираются по-русски
и переводятся вызовом `NdstI18n.apply(контейнер)` — тогда движок помнит исходник
и язык можно переключать сколько угодно раз. Строки с числами внутри переводятся
через `NdstI18n.t('Шаг {n} из 4', { n: 2 })` и перерисовываются по событию
`dia:langchange`. Склонения и названия месяцев отдаёт движок:
`NdstI18n.plural()` и `NdstI18n.months()`.

**Важно:** узбекский и английский переводы медицинских формулировок сделаны
без участия носителя языка. Перед публикацией их должен вычитать врач,
владеющий языком, — особенно рекомендации и
терминология дисплазии соединительной ткани.

## API

| Метод | Путь | Кто | Что делает |
|---|---|---|---|
| `POST` | `/api/assessments` | все | Сохраняет анкету, возвращает `public_id` |
| | | | Поля `diet`, `carbs`, `blood`, `dysplasia` необязательны |
| `POST` | `/api/assessments/pdf` | все | PDF-сводка по ответам анкеты, ничего не сохраняет |
| `GET` | `/api/assessments/{public_id}` | по коду | Одна оценка |
| `GET` | `/api/assessments/{id}/pdf?lang=` | врач | PDF-сводка сохранённой оценки |
| `GET` | `/api/assessments` | врач | Список с фильтрами `level`, `follow_up`, `q` |
| `PATCH` | `/api/assessments/{id}/follow-up` | врач | Отметка «нужен контроль» |
| `PATCH` | `/api/assessments/{id}/label` | врач | Метка пациента |
| `PUT` | `/api/assessments/{id}/dst` | врач | Осмотр по полной шкале ДСТ, индекс считает сервер |
| `DELETE` | `/api/assessments/{id}/dst` | врач | Вернуть степень ДСТ по ответам родителя |
| `GET` | `/api/clinic/stats?days=` | врач | Показатели кабинета и риск диабета в группах по ДСТ |
| `GET` | `/api/clinic/report?days=` | врач | Отчёт за период: уровни, степени, частые факторы |
| `GET` | `/api/clinic/export.csv` | врач | Выгрузка оценок в CSV с учётом фильтров |
| `GET` | `/api/admin/settings` | врач | Профиль; админу — код клиники и список врачей |
| `POST` | `/api/admin/code` | админ | Создать новый код клиники |
| `PATCH` | `/api/admin/password` | врач | Смена своего пароля |
| `PATCH` `DELETE` | `/api/admin/doctors/{id}` | админ | Права врача и удаление доступа |
| `POST` | `/api/auth/register` | — | Регистрация врача по коду клиники |
| `POST` | `/api/auth/login` · `/logout` | — | Вход и выход врача |
| `GET` | `/api/auth/me` | врач | Текущий врач |
| `POST` | `/api/patient/register` · `/login` · `/logout` | — | Учётная запись родителя |
| `GET` | `/api/patient/me` | родитель | Текущий родитель |
| `GET` `POST` | `/api/patient/children` | родитель | Список и добавление детей |
| `PATCH` `DELETE` | `/api/patient/children/{id}` | родитель | Правка и удаление профиля |
| `GET` | `/api/patient/assessments` | родитель | Только свои оценки |
| `POST` | `/api/patient/assessments/link` | родитель | Привязать анкету по коду |
| `PATCH` | `/api/patient/assessments/{id}/child` | родитель | Перенести оценку в другой профиль |

Что важно знать про эти ручки:

- **Балл считает сервер.** Присланный клиентом `score` игнорируется: сервер
  пересчитывает результат по ответам. Клиенту доверять нельзя.
- **Ключи проверяются по белому списку.** Неизвестный симптом, фактор, признак
  дисплазии, вариант питания или группа крови — `422`.
- **PDF готовит браузер на сервере.** Кнопка «Скачать PDF» отправляет ответы
  на `/api/assessments/pdf`. Сервер открывает страницу результата в Edge,
  Chrome или Chromium без окна (`/assessment?print=…` рисует итог сразу, без
  шагов и анимаций) и сохраняет её печатью. Правила печати те же, что у кнопки
  «Распечатать», поэтому файл совпадает с распечаткой. Без такого браузера на
  сервере адрес отвечает `503`, а кнопка подсказывает сохранить PDF через
  печать; путь к браузеру можно задать `NDST_BROWSER`. Одновременно готовятся
  не больше двух файлов, у каждого запуска свой временный профиль. Код оценки
  попадает в файл, только если такая оценка существует.
- **PDF отдельного пациента у врача.** Кнопка рядом с кодом оценки в таблице
  вызывает `GET /api/assessments/{id}/pdf`. Ответы берутся из базы, а не от
  клиента, документ тот же, но с датой прохождения анкеты, кодом, меткой
  пациента в шапке и осмотром врача по шкале ДСТ, если он проведён. Имя файла —
  `NDST-<код>-<дата>.pdf`, с меткой — через `filename*`, потому что метка
  бывает кириллицей.
- **Старый клиент не ломается.** Поля, добавленные позже (`diet`, `carbs`,
  `blood`, `dysplasia`), имеют значения по умолчанию: анкета без них
  сохраняется и считается как прежде.
- **Анкета имя ребёнка не собирает.** Оценка опознаётся по случайному
  `public_id`; человеческую метку при желании ставит врач. Имя, которое родитель
  вводит в своём кабинете, хранится в таблице `children` и в клиническую выдачу
  не попадает: запросы врача идут без соединения с этой таблицей, поэтому
  `child_name` у него всегда пустой.
- **Поле `source`** отражает, кто заполнял анкету: `clinic`, если на первом
  шаге выбран «Медицинский работник», иначе `parent`.
- **Кабинеты изолированы.** `/api/patient/*` требует сессию родителя,
  `/api/assessments` и `/api/clinic/*` — сессию врача; чужая роль получает `401`.
  Родитель видит только записи со своим `parent_id`, а привязать оценку к чужому
  ребёнку нельзя — `404`. Если анкета уже принадлежит другому кабинету,
  повторная привязка отдаёт `409`.
- **Пароли** — scrypt (N=2¹⁵, r=8) со своей солью у каждого. Ответ на неверную
  почту занимает столько же времени, сколько на верную.
- **Сессия** — cookie с HMAC-подписью, `HttpOnly`, `SameSite=Lax`, срок 12 часов.
  Состояние на сервере не хранится.
- **Вход ограничен**: пять неудач за пять минут на связку IP+почта, дальше `429`.
  Счётчик общий для обоих кабинетов (`backend/ratelimit.py`).

Не сделано и требуется перед публикацией: журнал доступа к данным, разграничение
прав между врачами (сейчас любой вошедший видит все оценки), резервное копирование.

## Заглушки, которые нужно заменить

Домен `ndst.app` придуман для примера. Заменить перед публикацией:

- `info@ndst.app` — контакт в подвале лендинга;
- `ndst.app / doctor / overview` — адрес в макете кабинета на лендинге;
- `demo@ndst.app` и `parent@ndst.app` — демонстрационные учётки врача
  и родителя (или отключить обе через `NDST_SEED_DEMO=0`).

## Кто заводит врачей

Регистрации «с улицы» у врача нет: учётная запись создаётся по коду клиники.
Страница регистрации — `/register`, ссылка на неё есть на странице входа.

Всем этим управляет администратор в кабинете, раздел **«Настройки»**: там видно
текущий код, его можно скопировать и создать новый, есть список врачей с правами
и смена своего пароля. Командная строка для этого не нужна.

- Администратор — врач с ролью `admin`. Первый врач в базе получает её сам
  (демо-учётка или тот, кого завели первым).
- Права выдаются и снимаются кнопкой в списке врачей; последнего администратора
  разжаловать или удалить нельзя, себя удалить тоже нельзя.
- «Убрать доступ» удаляет учётную запись врача. Оценки остаются.
- Код хранится в `data/clinic_code.txt`. Если задать `NDST_CLINIC_CODE`, код
  берётся оттуда, а кнопка «Создать новый» отключается.
- `python share.py status` по-прежнему печатает код, а `share.py start` — вместе
  со ссылкой; это для тех случаев, когда в кабинет ещё никто не вошёл.

Подбор кода ограничен тем же счётчиком, что и вход: пять неудач за пять минут
на IP, дальше `429`. Первый врач в пустой базе по-прежнему создаётся
демонстрационным (`NDST_SEED_DEMO=0` это отключает).

## Что умеет кабинет врача

- **Список оценок** с фильтрами по уровню риска, повторному контролю и наличию
  ДСТ, поиском по коду и метке, сортировкой и страницами.
- **Карточка оценки** (нажать на код в таблице): метка пациента и отметка
  «нужен повторный контроль». Отметку видит родитель в своём кабинете.
- **Осмотр по шкале ДСТ** — полный список из 44 признаков; заменяет степень,
  посчитанную по ответам родителя, и переносится на следующие анкеты ребёнка.
- **PDF по каждой оценке** и **выгрузка CSV** с учётом текущего фильтра.
- **Анализ риска** — сравнение групп с ДСТ и без неё. Единица сравнения —
  ребёнок: у ребёнка берётся последняя анкета, анкеты без профиля считаются
  сами по себе.
- **Статистика** — отчёт за 30, 90 или 365 дней: сколько анкет, средний риск,
  распределение уровней и степеней ДСТ, десять самых частых факторов.
- **Настройки** — профиль и пароль, код клиники и список врачей (для админа).

## Приватность

Расчёт по-прежнему идёт в браузере. На сервер анкета попадает **только** после
явного нажатия «Сохранить» на экране результата — тогда родитель получает
короткий код, по которому врач откроет анкету. Тексты на сайте это отражают:
обещания «данные никуда не уходят» заменены на «отправка только по вашей кнопке».

Кабинет пациента этого не меняет. Вошедший родитель на экране результата может
сразу указать, кому из детей засчитать анкету, — сохранение всё так же по кнопке.
Имя ребёнка вводится только в кабинете и остаётся в нём: анкета имени не
спрашивает, врач видит оценку под кодом. Пройденную без входа анкету родитель
привязывает к кабинету сам, по коду с экрана результата.

## Модель оценки риска

Прозрачная балльная модель — `frontend/scripts/assessment.js`, экспортируется как
`window.NdstModel` (`SYMPTOMS`, `RISKS`, `DURATION`, `classifyBMI`, `calculate`).

1. Каждому признаку присвоен вес, отражающий клиническую значимость:
   классические симптомы (жажда 18, полиурия 16, потеря веса 16) весят больше,
   чем факторы образа жизни (низкая активность 5, сладкие напитки 4).
   Семейный анамнез собирается по каждому родственнику отдельно: диабет 1 типа
   у отца, у матери и у брата или сестры — по 14 баллов. Бабушки и дедушки
   по просьбе заказчика (16.09.2026) из анкеты убраны, а аутоиммунные болезни
   родителей перечислены поимённо: тиреоидит Хашимото, болезнь Грейвса,
   витилиго, целиакия, ревматоидный артрит и болезнь Аддисона — по 5 баллов
   каждая. Добавлены перенесённые вирусные инфекции (энтеровирусы, аденовирусы)
   — 6 баллов и осложнения беременности или родов — 4.
2. ИМТ считается по росту и весу и сравнивается с ориентировочными
   перцентильными границами по возрасту и полу (`BMI_REF`, приближены к кривым
   CDC). Отклонение добавляет от 6 до 12 баллов.
3. Сумма баллов переводится в шкалу 0–100 насыщающей кривой
   `100 * (1 - exp(-total / 62))` — первые значимые признаки дают наибольший
   прирост, а редкие сочетания не выбивают шкалу за пределы.
4. Поверх баллов работает клиническое правило: классическая триада
   (жажда + полиурия + потеря веса или ночное недержание) поднимает оценку
   минимум до 70.
5. Отдельно учитываются питание (характер рациона до 6 баллов, доля углеводов
   до 7) и условия жизни (стресс в семье 4, ограниченные материальные
   возможности 3).
6. Уровни: < 25 низкий, 25–59 умеренный, ≥ 60 высокий риск диабета.

Признаки дисплазии соединительной ткани в процент риска **не входят** — у них
своя шкала, см. ниже.

### Дисплазия соединительной ткани: шкала ДСТ

Проект назван по этой теме: НДСТ — фон, на котором нарушения углеводного обмена
выявляют раньше. По решению заказчика степень дисплазии считается отдельно от
риска диабета и по той же системе, что в калькуляторе DST для детей. Так детей
с ДСТ и без неё можно сравнивать: если бы признаки дисплазии добавляли баллы
к риску, сравнение групп оказалось бы замкнутым на само себя.

Шкала — `backend/dst.py`, копия для браузера — `frontend/scripts/dst.js`
(`window.NdstDst`):

- 44 фенотипических признака с весами 1–5;
- три признака с градацией — растяжимость кожи, мышечная гипотония,
  гипермобильность по Бейтону: нет 0, умеренно 3, выраженно 5;
- тесты Штейнберга и Уокера—Мёрдока вместе дают один признак арахнодактилии:
  оба отрицательны 0, положителен один 3, оба 5;
- индекс — сумма баллов; степень: 0–15 — недостаточно фенотипических признаков,
  16–25 — I, 26–35 — II, ≥ 36 — III. Отдельно считаются признаки, отмеченные
  всего, и значимые (вес 4–5);
- 29 ассоциированных аномалий органов учитываются отдельным числом и в индекс
  не входят: пороги степеней рассчитаны только на фенотипические признаки.

Заполнить шкалу можно двумя путями:

1. **Родитель** на шаге 4 анкеты отмечает признаки прямо из шкалы: 19 самых
   частых фенотипических признаков с их баллами, два признака с градацией
   (гипермобильность по Бейтону и растяжимость кожи — галочка означает
   умеренную степень, `PARENT_GRADE`) и 6 малых аномалий развития внутренних
   органов. Список задан в `PARENT_FORM` (`frontend/scripts/dst.js`) и рисуется
   скриптом, поэтому подписи и баллы совпадают с осмотром врача. Анкета
   присылает их полем `dst`. Старый короткий список из 11 признаков остаётся
   в `PARENT_MAP` — по нему пересчитываются анкеты, сохранённые раньше.
2. **Врач** в кабинете нажимает на ячейку «ДСТ» в таблице оценок и заполняет
   полный осмотр. Он заменяет предварительную степень; кнопка «Вернуть ответы
   родителя» откатывает осмотр.

Раздел кабинета «Анализ риска» сравнивает риск диабета по группам: без ДСТ,
ДСТ I, II и III степени, и все дети с ДСТ вместе. Для каждой группы — число
оценок, средний риск, доли низкого, умеренного и высокого риска и сколько из
них осмотрено врачом. Это сравнение групп, а не доказательство связи.

При первом запуске после обновления база сама получает колонки `dst_*`,
а сохранённые оценки пересчитываются: из их риска диабета уходят баллы
дисплазии, степень ДСТ считается по ответам родителя.

### Снятые блоки

Блок «Неотложные признаки» (ацетон, многократная рвота, спутанность сознания)
убран из анкеты по просьбе заказчика 16.09.2026. Вместе с ним сняты правило
«минимум 92 балла» и блок о неотложной помощи на экране результата. Поле
`urgent` больше не принимается API, колонка в базе осталась ради старых
записей. Признаки неотложных состояний по-прежнему названы в рекомендациях
и в кабинете родителя.

### Что собирается, но в балл не входит

Группа крови. Связь системы AB0 с риском диабета в исследованиях
противоречива, поэтому вес у неё нулевой: значение сохраняется, но на оценку
не влияет. Если появятся основания её взвешивать, достаточно задать `w`
в `BLOOD` в обеих копиях модели.

Видно её в трёх местах: на экране результата анкеты, в таблице оценок у врача
рядом с кодом и в кабинете родителя под разбором факторов. Собирать данные,
которые потом негде посмотреть, смысла нет.

На экране результата перечисляются все учтённые факторы с их вкладом и
значимые признаки, которых у ребёнка нет.

Модель существует в двух копиях: `frontend/scripts/assessment.js` считает в браузере,
`backend/scoring.py` пересчитывает на сервере. Расхождение между ними ловит тест:

```bash
python tests/run_all.py              # все проверки разом
python tests/test_model_parity.py    # 407 анкет и 312 осмотров по шкале ДСТ
```

Случаи перебирают набор признаков дисплазии любой длины, характер питания,
долю углеводов и группу крови, а для шкалы ДСТ — случайные осмотры врача и
осмотры ровно на порогах 15/16, 25/26 и 35/36. Тест также сверяет пороги и
баллы арахнодактилии с документом DST, проверяет, что аномалии органов не
попадают в индекс, а признаки дисплазии не меняют процент риска диабета.
Анкета, присланная без новых полей, тоже в наборе — старый клиент не должен
ломать расчёт.

API проверяет отдельный тест — на временной базе, рабочие данные в `data/`
он не трогает:

```bash
python tests/test_api.py    # роли и права, регистрация по коду, настройки,
                            # анкета и осмотр ДСТ, кабинет родителя, выгрузки
```

Ещё два теста следят за переводами:

```bash
python tests/test_labels_translated.py   # метки, которые выдаёт модель
python tests/test_pages_translated.py    # строки страниц и скриптов
```

Второй разбирает разметку и скрипты теми же правилами, что и движок i18n:
текстовые узлы, переводимые атрибуты и **все** строковые литералы скриптов —
включая склеенные из кусков и те, что кладут в переменную и только потом
отдают в `t()`. Заодно он ловит повторно объявленные ключи словаря:
`Object.assign` молча оставляет последнее значение, так что дубль ничего
не ломает, а просто тихо перетирает более ранний перевод.

Забытая строка не ломает страницу — она молча остаётся русской, поэтому такую
проверку приходится делать тестом.

**Важно:** результат — оценка факторов риска, а не медицинский диагноз.
Дисклеймер присутствует на лендинге, в анкете и в футере.
